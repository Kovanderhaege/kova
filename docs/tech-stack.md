## Bascule MP — décision du 10 novembre 2026

- Stack inchangée : reqwest 0.12.28, GPUI 0.2.2, cache chiffré age/SQLite et sessions du coffre. La sélection appartient au cœur client ; le desktop fournit les sessions par origine. Aucun annuaire, nouvelle autorisation ou nouveau protocole cryptographique.
- Candidats : uniquement la politique bilatérale signée conservée localement, sinon l'origine du manifeste. Vérifier le descripteur de fédération contre la clé approuvée et relire la chaîne de politiques avant les opérations. Les erreurs de transport et HTTP 5xx permettent un repli ; les refus d'accès, conflits, signatures et données invalides restent bloquants. Les erreurs HTTP conservent un statut typé même si un proxy renvoie une page non JSON.
- Reprise : réutiliser les événements chiffrés déjà persistés, sans régénérer identifiant ni état MLS. L'ordonnancement est limité à la conversation sélectionnée dans le panneau MP, hors thread UI, sans opérations concurrentes et avec délai croissant après échec. La fermeture du panneau arrête les nouvelles tentatives ; ce n'est pas un service système permanent.
- Références vérifiées le 2026-11-10 : [GPUI BackgroundExecutor::timer et spawn](https://docs.rs/gpui/0.2.2/gpui/struct.BackgroundExecutor.html). Les méthodes `reqwest::Error::{is_connect,is_timeout,status}` sont vérifiées dans le source officiel de reqwest 0.12.28 installé par Cargo (`src/error.rs`) ; la page docs.rs de cette version était inaccessible au navigateur. Le classement des erreurs et les intervalles de reprise sont des décisions Kova, pas une garantie de livraison des bibliothèques.

## Réplication MP — décision du 8 novembre 2026

- Périmètre du jalon 6 : synchronisation explicite serveur à serveur entre origines configurées, sans annuaire ni bascule automatique (jalon 7). Réutilisation de ring 0.17.14, reqwest 0.12.28, SQLx 0.8.6 et PostgreSQL 17 ; aucun nouveau protocole de chiffrement du contenu.
- Politique : tuple JSON canonique `kova-dm-replica-policy-v1`, conversation, version positive, empreinte SHA-256 de la politique précédente et liste triée de couples origine/clé publique Ed25519 de serveur. Les deux appareils du manifeste signent exactement ce contenu. Une proposition ou une signature seule ne donne aucun droit. Le serveur contrôle la succession sous verrou ; aucune union automatique des branches concurrentes.
- Fédération fermée : clés de pairs épinglées par configuration, correspondant aux descripteurs approuvés. Authentification applicative Ed25519 des requêtes et réponses en complément de HTTPS ; HTTP limité à la boucle locale de développement. Origines source/destination, méthode, chemin, empreinte du corps, nonce et échéance sont liés à la signature ; nonces consommés durablement. Aucun routage vers une adresse fournie librement par un utilisateur, aucune redirection HTTP.
- Reprise : curseurs propres à chaque réplica, événements globaux immuables, déduplication exacte, dépendances présentes avant insertion. L'ordre d'affichage topologique avec départage UUID existant demeure indépendant des curseurs. Les politiques retirant un réplica interdisent les nouveaux transferts une fois connues ; elles ne peuvent effacer ses copies ni être connues instantanément pendant une partition.
- Références consultées le 2026-11-08 : [ring Ed25519KeyPair 0.17.14](https://docs.rs/ring/0.17.14/ring/signature/struct.Ed25519KeyPair.html), [verrous PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html). Ces sources valident les primitives et transactions employées ; le contrat de consentement et de fédération reste un protocole applicatif Kova, pas un protocole audité par ces projets. Les détails livrés et limites sont consignés dans `replication.md` après validation.

## MP privés — 8 novembre 2026

Cette section remplace les réserves historiques « E2EE à sélectionner » ci-dessous ; la décision de réplication du jalon 6 figure plus haut.

- MLS RFC 9420 via OpenMLS `=0.8.1`, fournisseur Libcrux `=0.3.1` et credentials Basic `=0.5.0`, isolés dans `kova-crypto` côté client. Suite X25519/AES-128-GCM/SHA-256/Ed25519, clés distinctes de l'authentification Kova. OpenMLS est pré-1.0 et le toolchain local est Rust 1.99.1. Choix borné au prototype, comparaison Signal, audit et limites détaillés dans [la décision E2EE](decisions/e2ee.md). Aucune dépendance MLS du serveur.
- Un appareil explicitement vérifié par participant dans chaque conversation. Le KeyPackage MLS est lié par signature à l'identité et à l'autorisation d'appareil v2 ; le Welcome doit produire exactement les deux credentials et clés de signature attendus. Aucun ajout, commit MLS distant ou transfert d'historique implicite. Après expiration des attestations initiales (au plus 24 h), nouvel échange de preuves et nouvelle conversation nécessaires ; pas de renouvellement de roster dans ce jalon.
- Enveloppes : tuples JSON typés UTF-8, domaines `kova-dm-device-v1`, `kova-dm-conversation-v1`, `kova-dm-event-v1`, tableaux de parents triés. Le plaintext MLS lie également identifiant d'événement, conversation et parents. La signature d'appareil porte sur les octets canoniques exacts, jamais sur le JSON reçu tel quel. Les objets complets embarqués ont l'ordre des champs des structs Rust déclaré dans le contrat.
- Cache privé : age `=0.12.1` déjà utilisé, destinataire X25519 généré localement et secret dans Windows Credential Manager. SQLite ne reçoit qu'un blob age contenant état MLS, historique et file d'envoi ; commit SQLite FULL sous verrou interprocessus de profil avant tout envoi. Une opération cryptographique travaille sur une copie et ne remplace l'état durable qu'après validation complète. Cette solution MVP réécrit le snapshot entier : coût croissant avec l'historique, pas de garantie de suppression physique des anciennes clés dans WAL/sauvegardes, ni de résistance au rollback par un attaquant contrôlant le disque. Référence consultée le 2026-11-08 : [age 0.12.1 Encryptor, usage programmatique X25519](https://docs.rs/age/0.12.1/age/struct.Encryptor.html).
- Relais unique explicitement signé dans le manifeste, indépendant des communautés. Création atomique et consommation unique du KeyPackage destinataire ; verrou conversation, déduplication exacte, parents présents et curseur local transactionnel pour les événements. REST paginé ; synchronisation manuelle, pas de notification WS MP ni de réplication dans ce jalon. Les verrous PostgreSQL/SQLx déjà validés pour les jalons 3/4 sont réutilisés.

## 1. Rust et séparation des composants

- **Versions :** édition Rust 2024, workspace Cargo avec `resolver = "3"`. L'édition exige au moins Rust 1.85 ; ce seuil n'est pas un MSRV validé pour l'ensemble des dépendances. Aucun `rust-version` ni toolchain exacte n'est fixé ; CI sur `stable`, build Docker sur `rust:1-bookworm`.
- **Approche :** `kova-server` porte HTTP et PostgreSQL ; `kova-protocol` les formats signés ; `kova-identity` la vérification publique ; `kova-client-core` les secrets et services clients ; `apps/desktop` l'interface. Les bibliothèques partagées et le cœur client ne dépendent pas du serveur. Conserver `Cargo.lock` et utiliser `--locked` pour les vérifications et builds.
- **Raison :** partager les contrats sans coupler les clients au stockage serveur. Ne créer d'autres crates que pour une fonctionnalité testable ; ne pas anticiper une infrastructure de microservices.
- **Références :** [édition 2024](https://doc.rust-lang.org/edition-guide/rust-2024/index.html), [résolution Cargo](https://doc.rust-lang.org/cargo/reference/resolver.html#resolver-versions). Vérifiées le 2026-11-06.

## 2. API serveur asynchrone

- **Versions :** Axum `0.8` → **0.8.9**, Tokio `1` → **1.54.1**, Serde `1` → **1.0.229**, serde_json `1` → **1.0.154**.
- **Approche :** routeur Axum, état partagé via `State`, écoute `TcpListener`, `axum::serve` et arrêt gracieux. Tokio active `macros`, `rt-multi-thread`, `net`, `signal`, `time`. Échanges HTTP JSON sous `/api/v1` ; sonde `/health/ready` interrogeant réellement PostgreSQL.
- **Raison :** prolonger le serveur modulaire existant avec le même runtime que SQLx. Ne pas reprendre les exemples d'anciennes versions reposant sur `axum::Server`.
- **Limite :** le chat et WebSocket ne sont pas implémentés ; leur présence dans la cible MVP ne constitue pas un choix de bibliothèque supplémentaire.
- **Références :** [Axum 0.8.9](https://docs.rs/axum/0.8.9/axum/), [Tokio 1.54.1](https://docs.rs/tokio/1.54.1/tokio/). Vérifiées le 2026-11-06.

## 3. Persistance serveur et migrations

- **Versions :** PostgreSQL **17**, image `postgres:17-alpine` (mineure et digest non figés) ; SQLx `0.8` → **0.8.6**.
- **Approche :** pool PostgreSQL, SQL explicite et transactions ; SQLx sans fonctionnalités par défaut, avec `runtime-tokio`, `postgres`, `macros`, `migrate`. Les migrations embarquées par `sqlx::migrate!()` sont appliquées au démarrage ; `build.rs` surveille leur répertoire.
- **Raison :** conserver les garanties transactionnelles des sessions, invitations et adhésions. Les migrations déjà appliquées restent immuables ; toute évolution passe par une nouvelle migration. `docs/schema.sql` reproduit les migrations livrées ; `docs/migrations.md` distingue celles-ci des propositions futures.
- **Limites :** PostgreSQL 17 appartient à une branche supportée selon la politique officielle consultée. SQLx n'active aucun backend TLS dans le manifeste actuel : ne pas considérer la connexion à une base distante comme sécurisée sans décision de déploiement supplémentaire.
- **Références :** [SQLx 0.8.6, runtime et TLS](https://docs.rs/sqlx/0.8.6/sqlx/), [support PostgreSQL](https://www.postgresql.org/support/versioning/). Vérifiées le 2026-11-06.

## 4. Identité et sessions

- **Versions :** protocole Kova **v1** ; ring `0.17` → **0.17.14**, sha2 `0.10` → **0.10.9**, hex `0.4` → **0.4.3**. Le serveur utilise rand `0.8` → **0.8.8** ; les autres versions de rand/sha2 du lockfile sont transitives.
- **Approche :** racine et appareil Ed25519 générés côté client ; autorisation de l'appareil signée par la racine, challenge contextualisé puis preuve signée par l'appareil. Identifiants dérivés par SHA-256. Conserver exactement les octets signés v1 et les vecteurs de test partagés.
- **Sessions :** Bearer desktop limité à une heure et lié à l'origine ; cookie historique limité à sept jours pour l'outil Python. L'échéance d'autorisation borne aussi la session. Empreintes des jetons côté base, rejet du mélange des transports, révocation locale et preuves conservées par la migration 0003.
- **Raison et alternative historique :** identité indépendante de l'hébergeur ; aucun secret privé reçu par le serveur. L'authentification par mot de passe a été retirée par 0002 : ne pas la réintroduire en copiant l'ancien modèle.
- **Limite :** Ed25519 assure ici l'authenticité ; aucun protocole E2EE de messages n'est choisi. Le journal de révocations et la fraîcheur sont définis en section 9 ; la propagation reste explicite, sans réplication serveur-à-serveur.
- **Références :** [signatures ring 0.17.14](https://docs.rs/ring/0.17.14/ring/signature/index.html), [contrat Kova](protocol.md), [modèle de menace](threat-model.md). Vérifiés le 2026-11-06 ; les règles Kova sont propres au projet, pas une recommandation de ring.

## 6. Interface native Windows : choix de prototype

- **Versions :** GPUI épinglé à **`=0.2.2`**, fonctionnalités par défaut désactivées, `windows-manifest` activé ; unicode-segmentation `1` → **1.13.3**.

Ce choix existant est donc une évaluation bornée, pas une stack UI stable validée pour production. Conserver la version exacte et vérifier les exemples de cette version.

## 9. Clôture du jalon 2 — décisions du 6 novembre 2026

- Sauvegarde : `age = 0.12.1`, format age v1, chiffrement par phrase secrète humaine via scrypt. Aucun format de chiffrement maison. La bibliothèque déclare encore un statut pré-1.0/bêta : exception explicite et bornée au MVP, retenue pour sa compatibilité avec le format age et les outils rage/Go ; tests erreur de mot de passe, corruption et restauration obligatoires. Référence : https://docs.rs/age/0.12.1/age/ . Sauvegarde de la racine uniquement, restauration avec un nouvel appareil.
- Association : demande publique éphémère signée par le nouvel appareil, vérification de son empreinte par un canal authentifié (en personne ou canal déjà vérifié), puis réponse signée par la racine et liée à cette demande. Fichiers publics échangés explicitement ; aucune clé privée dans la demande/réponse. QR visuel différé, non requis pour cette association manuelle. L'appareil associé reçoit une autorisation, jamais la racine.
- Fraîcheur : autorisations d'appareil bornées à 24 h ; renouvellement signé par la racine, aucun serveur d'identité central. À échéance, refus de connexion et de session. Les appareils associés doivent recevoir une autorisation renouvelée par l'appareil racine. Les anciennes autorisations de 90 jours ne sont plus acceptées pour de nouvelles sessions ; les sessions existantes seront invalidées par migration.
- Journal : ensemble monotone de révocations racine signées, domaine v1 déjà établi, identifiant d'événement SHA-256 du payload canonique. Pas de compteur global ou d'ordre d'horloge : une révocation est définitive et l'union des preuves converge. Chaque instance conserve la preuve et la fournit aux clients authentifiés. Publication indépendante de session, mais exigeant la signature racine vérifiée et soumise au quota. Propagation explicite aux instances connues, avec statut par instance ; une instance non jointe peut ignorer une révocation au maximum jusqu'à échéance de l'autorisation (24 h). Aucune garantie de propagation instantanée revendiquée.
- UI : travail réseau/chiffrement/coffre hors thread GPUI, via tâches de fond puis mise à jour d'entité ; contexte GPUI 0.2.2 existant. Référence : https://docs.rs/gpui/0.2.2/gpui/struct.Context.html . Le jalon 2 ne sélectionne pas de protocole E2EE de messages.

- Correctif de revue (2026-11-06) : autorisation `kova-device-v2` incluant `issued_at` et `expires_at`, durée totale positive ≤ 86400 s, émission non future et expiration future. Le contrôle de seule échéance glissante laisserait ressurgir des certificats v1 de longue durée pendant leur dernier jour. Le serveur refuse les autorisations v1, sans changer leurs anciens octets canoniques ; les clients doivent renouveler depuis la racine. Les domaines challenge/révocation restent v1. Ed25519/ring restent inchangés ; référence vérifiée : https://www.rfc-editor.org/rfc/rfc8032#section-5.1.7 (vérification de la signature sur le message exact). La fenêtre 24 h et le format applicatif sont une décision du projet, pas une prescription de cette RFC.

## 10. Communautés — 7 novembre 2026

- Stack inchangée : Axum 0.8.9, SQLx 0.8.6, PostgreSQL 17, reqwest 0.12.28 et GPUI 0.2.2. Toute identité ayant un profil local peut créer une communauté ; l'administrateur d'instance n'obtient aucun accès implicite aux communautés.
- Propriétaire dérivé de `communities.owner_id`, rôles stockés `member`/`moderator`. Membres : lecture ; propriétaire/modérateurs : salons et invitations ; propriétaire seul : attribution des rôles ; exclusion par propriétaire, ou par modérateur d'un simple membre. Propriétaire non excluable, pas de transfert dans ce jalon.
- Création communauté/adhésion propriétaire/salon `général` dans une transaction. Les opérations ciblées verrouillent d'abord la communauté (`FOR UPDATE`), puis relisent les droits dans une nouvelle requête ; adhésion par invitation et exclusion suivent le même ordre. Cela sérialise les mutations d'une communauté et évite les décisions sur un rôle périmé après attente de verrou. La liste générale filtre directement par adhésion.
- Exclusion persistante du profil local (lié de façon unique à l'identité), dans une nouvelle table, puis suppression de l'adhésion dans la même transaction. Une nouvelle invitation ne contourne pas l'exclusion. Les autres communautés et sessions restent valides. Aucun droit MP n'en découle.
- Invitations : jeton aléatoire de 32 octets, seule empreinte SHA-256 stockée, usage unique, durée demandée entre 1 seconde et 7 jours ; réutilisation du challenge signé join pour la première connexion ; `/invites/redeem` pour une session déjà active. Durée proposée dans le desktop : 24 h. Pas de jeton en URL ni en cache client. Ressource invisible : 404 ; droit insuffisant d'un membre : 403. Limite de corps existante et réponses `no-store` conservées.
- Références consultées le 2026-11-07 : [verrous PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html), [transactions SQLx 0.8.6 et rollback à l'abandon](https://docs.rs/sqlx/0.8.6/sqlx/struct.Transaction.html). La matrice de droits et la durée des invitations sont des choix du produit, pas des prescriptions de ces sources.

- Tests WS : Python `websockets==17.3`, API synchrone `websockets.sync.client.connect` en context manager (sans API asyncio legacy), uniquement dans les tests. Référence consultée le 2026-11-07 : https://websockets.readthedocs.io/en/stable/reference/sync/client.html . UUID v4 : fonctionnalité de `uuid` 1 déjà verrouillé dans le workspace, identifiants d'idempotence non secrets.
- Migration 0006 : recaler `last_seq` sur les messages historiques ; refuser explicitement une histoire à trous sans la renuméroter. Les migrations 0001–0005 restent immuables.
