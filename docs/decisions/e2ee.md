# Décision E2EE — conversations privées 1:1

Décision du 8 novembre 2026 : employer MLS (RFC 9420) via OpenMLS `0.8.1` et son fournisseur officiel libcrux `0.3.1` dans le nouveau crate client `kova-crypto`. Les manifestes désactivent les fonctionnalités Cargo par défaut et n'activent que `libcrux-provider`; le fournisseur offre le stockage mémoire OpenMLS et le ciphersuite MLS X25519/AES-128/Ed25519 choisi. Cette version maintenue inclut les correctifs d'audit publiés dans la branche 0.8.x. Elle est retenue à la place de 0.9.0 car ses dépendances HPKE évitent une incompatibilité Cargo avec `age 0.12.1` : la branche 0.9 résout une version stable de `kem` qui casse la compilation de `ml-kem 0.2.1` exigé par age. 0.8.1 fonctionne avec la contrainte `kem` compatible avec age. Ce n'est pas un choix de protocole PQ. Le choix reste borné au MVP et à deux participants ; OpenMLS est encore pré-1.0, donc son format de stockage et ses API demandent un suivi de version explicite. Le protocole garde une voie vers les groupes après MVP. Le choix ne met pas en œuvre la réplication inter-instances du jalon 6.

OpenMLS est du Rust natif et expose le flux MLS asynchrone par KeyPackage, Welcome et messages applicatifs. Signal Protocol reste une option maintenue, mais `libsignal` est distribué sous AGPL-3.0-only et sa surface d'intégration vise les clients Signal via bridges Java/Swift/TypeScript. OpenMLS sous MIT s'aligne avec les dépendances Rust natives et la répartition arrêtée le 15 novembre 2026 : GPL-3.0-only pour le desktop/cœur client, Apache-2.0 pour `kova-crypto` (voir [licensing.md](licensing.md)). Cette préférence ne remplace pas une revue de licence des dépendances transitives avant distribution.

L'audit indépendant SRLabs publié le 27 mai 2026 rapporte huit constats, dont un de gravité haute : sept corrections ont été fusionnées et publiées dans OpenMLS 0.8.1 et 0.7.3 ; le constat restant était de faible gravité et encore en cours de correction dans ce compte rendu. Cet audit ne garantit pas l'absence de défauts dans OpenMLS 0.8.1, le fournisseur libcrux, ses dépendances, l'intégration Kova ou le modèle de stockage. Le fichier verrou fixe `kem` à la version de prépublication compatible avec le `ml-kem` requis par age ; vérifier que cette contrainte tient lors des mises à jour. OpenMLS 0.8.1 est distribué sous MIT et supporte le toolchain Rust du projet.

Limitation connue d'OpenMLS 0.8.1 : `PrivateMessageIn::decrypt` exécute `debug_assert!(false, "Ciphertext decryption failed")` sur un échec AEAD avant de retourner `MessageDecryptionError::AeadError`. Les builds debug paniquent sur un ciphertext altéré ; les builds release retournent l'erreur. La version officielle 0.9.0 a supprimé cet assert, mais sa dépendance Cargo optionnelle `openmls_rust_crypto` `0.6.0` tire un autre `kem` incompatible avec `age 0.12.1`. Le wrapper intercepte le panic OpenMLS en debug, invalide ce groupe et retourne `InvalidMessage`. L'appelant doit abandonner le client crypto après toute erreur de déchiffrement, car MLS peut avoir fait avancer l'état du ratchet. Références de code : [source officielle 0.8.1](https://github.com/openmls/openmls/blob/openmls-v0.8.1/openmls/src/framing/private_message_in.rs) et [source officielle 0.9.0](https://github.com/openmls/openmls/blob/openmls-v0.9.0/openmls/src/framing/private_message_in.rs).

Chaque leaf credential contient explicitement `kova1-…` et l'identifiant d'appareil. Le credential Basic MLS n'authentifie pas lui-même le lien entre identité et clé de signature : l'application doit vérifier ce lien à travers l'autorisation d'appareil Kova signée. Le consommateur valide ces attestations avant d'accepter une conversation/Welcome et contrôle ensuite que le roster MLS correspond exactement aux participants autorisés. Les clés E2EE sont créées indépendamment des clés racine et appareil.

Les événements applicatifs utilisent les messages MLS chiffrés ; le serveur relaie seulement les octets opaques. Le cache client conserve le texte nécessaire à l'affichage. L'état MLS et les clés persistantes doivent être chiffrés au repos, authentifiés contre les modifications et stockés côté client seulement. Le fournisseur de stockage OpenMLS est dans le modèle de confiance de la bibliothèque ; supprimer les anciennes clés doit réellement supprimer toutes les copies pour conserver la propriété de forward secrecy. Ne pas sérialiser le state MLS en clair dans le cache SQLite existant. Les mécanismes de réplication, les politiques de consentement, l'authentification serveur-à-serveur et la bascule automatique restent au jalon 6/7.
